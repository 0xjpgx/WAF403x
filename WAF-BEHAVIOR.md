# WAF behaviour matrix — where each engine inspects, what a block looks like, and what shape assumptions break

Desk research for the 403 sweep engine in `wafdetect.py`. Every row ends in a request shape and a differential signal the engine can assert on. No payloads were sent at third-party sites; everything below is vendor documentation, published research, or a header/body observation on a public page fetched 2026-11-22.

Evidence tags used inline:

- `[doc]` vendor documentation, URL on the same line.
- `[res]` published research, URL on the same line.
- `[obs]` response I fetched and read while writing this.
- `?` best-effort recall, not verified — the sweep must treat it as a hypothesis, not a fact.

Two research anchors carry several rows and are worth reading in full before tuning rules:

- WAFFLED, *Exploiting Parsing Discrepancies to Bypass Web Application Firewalls* — 1207 confirmed bypasses across AWS WAF, Azure WAF, Google Cloud Armor, Cloudflare and ModSecurity on NGINX, using `multipart/form-data`, `application/json` and `application/xml`; vendors acknowledged. https://arxiv.org/abs/2503.10846
- PortSwigger, *Bypassing WAFs with the phantom $Version cookie* — RFC2109 cookie re-parsing defeats value-level signatures, with a live AWS WAF example. https://portswigger.net/research/bypassing-wafs-with-the-phantom-version-cookie

Generic encoding/obfuscation classes (multiple encodings, overlong UTF-8, `%u`, case, whitespace) come from PortSwigger's encoding reference https://portswigger.net/web-security/essential-skills/obfuscating-attacks-using-encodings and Soroush Dalili's request-encoding paper https://soroush.me/downloadable/request-encoding-to-bypass-web-application-firewalls.pdf. Path-confusion between WAF and app parser is a documented class in arXiv's WAFFLED and Claroty's URL-parsing research https://claroty.com/team82/research/exploiting-url-parsing-confusion .

## 1. Cloudflare

| Field | Detail |
|---|---|
| Position | Global edge reverse proxy on proxied (orange-cloud) DNS records; origin is a normal server that stays reachable if you find its IP and it does not restrict to Cloudflare ranges. Cloudflare documents Authenticated Origin Pulls and Tunnel as the controls that stop direct-to-origin traffic. `[doc]` https://developers.cloudflare.com/fundamentals/reference/http-headers/ |
| Inspection / normalization | URL normalization is a switch: enabled, URLs are normalized before WAF custom rules, Workers and Access; disabled, the URL is forwarded to origin in its original form. Some baseline normalization always applies — two or more adjacent slashes collapse to one, and that cannot be disabled. `[doc]` https://developers.cloudflare.com/rules/normalization/ . Managed rules inspect the body up to 128 KB on Enterprise, 1 MB on Free, lower by default on other paid plans; `http.request.body.truncated` reports truncation. `[doc]` https://developers.cloudflare.com/waf/managed-rules/ . Cloudflare rewrites `accept-encoding` to `br, gzip`, strips `x-real-ip`, and removes headers whose names NGINX considers invalid (dots). `[doc]` https://developers.cloudflare.com/fundamentals/reference/http-headers/ |
| Block signature | Block action is a terminating action in rule order `[doc]` https://developers.cloudflare.com/waf/concepts/ . Block page: HTTP 403, `server: cloudflare`, `cf-ray`, body carries `cf-error-details` or the "Attention Required" / "Sorry, you have been blocked" text `[obs]`. Challenge is distinguishable by header, not status: the challenge response always carries `cf-mitigated: challenge` and `content-type: text/html` regardless of the requested resource type. `[doc]` https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/ |
| Weak spots | (a) Normalization-off mismatch: rules and origin see different strings, and `/%68ello` is the vendor's own example of two spellings of one path `[doc]` https://developers.cloudflare.com/rules/normalization/ . (b) Skip-rule ordering: a skip rule only bypasses execute rules listed after it, so placement decides whether a payload is inspected `[doc]` https://developers.cloudflare.com/waf/managed-rules/ . (c) Body truncation above the plan limit leaves the tail uninspected `[doc]` https://developers.cloudflare.com/waf/managed-rules/ . (d) Header mutation at the edge means a rule can match a value the origin never sees, and vice versa `[doc]` https://developers.cloudflare.com/fundamentals/reference/http-headers/ . (e) Direct origin if not firewalled to Cloudflare ranges `[doc]` (same headers page, Authenticated Origin Pulls / Tunnel). (f) Parsing differentials in multipart/JSON/XML were confirmed by Cloudflare as real `[res]` https://arxiv.org/abs/2503.10846 |
| Test | `GET /%61dmin HTTP/1.1` and `GET //admin HTTP/1.1` against the same resource, raw socket, then again with `..;/` inserted. Differential: 403 block page on the encoded form but 200/302 from origin on the other, or the reverse (baseline `//` collapse). Second test: 1.1 MB `application/x-www-form-urlencoded` body where the payload sits after byte 1,048,576 — a Free-plan zone cannot see it `[doc]` body limit. |
| Source | https://developers.cloudflare.com/rules/normalization/ ; https://developers.cloudflare.com/waf/managed-rules/ ; https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/ |

## 2. Akamai (Kona / App & API Protector, Ghost, Bot Manager)

| Field | Detail |
|---|---|
| Position | Edge CDN and reverse proxy. Origin protection is opt-in: Site Shield maps exist precisely so non-Akamai machines cannot reach origin, and you must allow Site Shield IPs through your own firewall. `[doc]` https://techdocs.akamai.com/site-shield/docs/allow-site-shield-ip-addresses-through-your-firewall |
| Inspection / normalization | Rule-based evaluation with per-attack-group risk scoring: each rule contributes a score, the group total decides whether the configured action fires, and an individual rule can be forced to Deny. `[doc]` https://techdocs.akamai.com/cloud-security/docs/set-protections . Body inspection limit and exact normalization order are not published in the pages read `?`. Bot Manager sets `_abck`/`bm_sz` sensors and can serve a denial page on HTTP 200 `[doc]`(secondary) https://www.statproxies.com/glossary/anti-bot-status-codes |
| Block signature | HTTP 403 with `Access Denied`, `Reference #18.x` reference number, `server: AkamaiGHost`; Microsoft documents exactly this page for Akamai-hosted properties. `[doc]` https://learn.microsoft.com/en-us/troubleshoot/windows-server/networking/access-denied-visit-website-hosted-akamai-cdn . Detector markers `x-akamai-request-id`, `ak_bmsc`, `akaas_*` `[obs]`. Bot Manager may return 200 with a denial/alternate body instead of 403 `[doc]`(secondary) https://www.statproxies.com/glossary/anti-bot-status-codes |
| Weak spots | (a) Score thresholds: a single low-scoring payload can stay under the group threshold while the origin still executes it — the engine's action is score-driven, not per-rule `[doc]` https://techdocs.akamai.com/cloud-security/docs/set-protections . (b) Status-only detection breaks when Bot Manager answers 200 `[doc]`(secondary) same URL. (c) Origin reachable whenever Site Shield is not deployed; Site Shield is a separate product you must enable `[doc]` https://techdocs.akamai.com/site-shield/docs/allow-site-shield-ip-addresses-through-your-firewall . |
| Test | Send one request with a single suspicious token and one with twelve; expect 200 on the first and 403 + `Reference #` on the second if the action is score-based. Then resolve historical A records and send `GET / HTTP/1.1` with the target `Host:` straight to the origin IP: 200 with no `Reference #` and no `AkamaiGHost` server header proves origin exposure. |
| Source | https://techdocs.akamai.com/cloud-security/docs/set-protections ; https://learn.microsoft.com/en-us/troubleshoot/windows-server/networking/access-denied-visit-website-hosted-akamai-cdn ; https://techdocs.akamai.com/site-shield/docs/allow-site-shield-ip-addresses-through-your-firewall |

## 3. AWS WAF with CloudFront

| Field | Detail |
|---|---|
| Position | Edge on CloudFront, or regional on ALB / API Gateway / AppSync. CloudFront forwards the request to the origin after the web ACL decision; origin exposure depends on the origin's own security group or S3 policy `[doc]` https://docs.aws.amazon.com/waf/latest/developerguide/cloudfront-features.html |
| Inspection / normalization | Nothing is decoded for you: transformations such as `URL_DECODE`, `HTML_ENTITY_DECODE`, `BASE64_DECODE`, `CMD_LINE` are per-statement opt-ins applied before matching. `[doc]` https://docs.aws.amazon.com/waf/latest/developerguide/waf-rule-statement-transformation.html . Limits: body 8 KB on ALB and AppSync; 16 KB default on CloudFront, API Gateway, Cognito, App Runner, Verified Access and Bedrock AgentCore, raiseable to 64 KB per web ACL. Headers: first 8 KB and first 200 headers. Cookies: first 8 KB and first 200 cookies; a single named header inspected alone is not subject to those limits. `[doc]` https://docs.aws.amazon.com/waf/latest/developerguide/waf-oversize-request-components.html . Oversize handling is a rule-statement setting `[doc]` same URL. |
| Block signature | Block → 403 (custom response body/status configurable). Challenge → HTTP **202** with `x-amzn-waf-action: challenge` plus a JS interstitial when `Accept: text/html`. CAPTCHA → HTTP **405** with `x-amzn-waf-action: captcha`. `[doc]` https://docs.aws.amazon.com/waf/latest/developerguide/waf-captcha-and-challenge-actions.html . Detector markers `x-amzn-requestid`, body `Request blocked` `[obs]`. A live AWS WAF challenge page serves `challenge.js` and a `gokuProps`/`awsWafCookieDomainList` blob `[obs]` (seen on wordfence.com). |
| Weak spots | (a) Cookie value analysis bypass: AWS WAF blocked `eval('test')` but allowed the same cookie re-encoded as an RFC2109 quoted string with octal escapes — `"\145\166\141\154\050\047\164\145\163\164\047\051"` — because the WAF does not decode quoted-string/octal cookie values `[res]` https://portswigger.net/research/bypassing-wafs-with-the-phantom-version-cookie . (b) Duplicate `Cookie:` headers are combined differently per framework, so a name can hide inside a value `[res]` same URL. (c) Body beyond the 8/16/64 KB window is unexamined; whether that leaks depends on the statement's oversize handling `[doc]` https://docs.aws.amazon.com/waf/latest/developerguide/waf-oversize-request-components.html . (d) 202 is not a pass — treating any non-403 as bypass is the classic false positive here `[doc]` captcha-and-challenge page. WAFFLED reports no successful bypasses against AWS WAF in its own set, so expect this engine to be the hardest of the five it tested `[res]` https://arxiv.org/abs/2503.10846 |
| Test | `Cookie: $Version=1; q="\145\166\141\154\050\141\154\145\162\164\050\061\051\051"` versus `Cookie: q=eval(alert(1))` on the same endpoint. Signal: 403 on the plain form, 200/origin response on the quoted-octal form, and the app must echo/execute the decoded value. Second test: 70 KB body with the payload at offset 65,000 — 403 for the marker at offset 0, 200 for the offset-65,000 copy. |
| Source | https://docs.aws.amazon.com/waf/latest/developerguide/waf-captcha-and-challenge-actions.html ; https://docs.aws.amazon.com/waf/latest/developerguide/waf-oversize-request-components.html ; https://portswigger.net/research/bypassing-wafs-with-the-phantom-version-cookie |

## 5. F5 BIG-IP ASM

| Field | Detail |
|---|---|
| Position | On-prem or virtual ADC/reverse proxy in front of the app; origin normally not publicly reachable because the BIG-IP holds the VIP `?`. |
| Inspection / normalization | Parameter-level inspection only exists for content types the policy has a profile for. JSON support is added by creating and attaching a JSON profile; without one, JSON is not treated as parameters. If JSON parsing fails, ASM raises the `Malformed JSON data` violation regardless of the tolerate-warnings setting. `[doc]` https://techdocs.f5.com/en-us/bigip-17-5-0/big-ip-asm-implementations/adding-json-support-to-an-existing-security-policy.html . Every transaction gets a support ID, violations or not. `[doc]` https://clouddocs.f5.com/api/irules/ASM__support_id.html |
| Block signature | HTTP 403 page: "The requested URL was rejected. Please consult with your administrator. Your support ID is: …". `[doc]` https://my.f5.com/manage/s/article/K000156619 . Detector markers `BIGipServer*`, `TS01*` cookies, `server: BigIP` `[obs]`. |
| Weak spots | (a) No JSON profile attached → body is not parsed into parameters, so signatures that match parameter values never see them; the same body is still parsed by the app `[doc]` https://techdocs.f5.com/en-us/bigip-17-5-0/big-ip-asm-implementations/adding-json-support-to-an-existing-security-policy.html . (b) "Malformed JSON data" means the parser had to be reachable at all — a body the app accepts but ASM calls malformed is a differential worth probing `[doc]` same URL. (c) Content-type switching (`application/json` → `text/plain`) changes which profile runs while many frameworks still parse JSON `[res]` WAFFLED content-type-removal class https://arxiv.org/abs/2503.10846 . |
| Test | `POST /api HTTP/1.1` with `Content-Type: application/json` and body `{"a":"<script>alert(1)</script>"}`, then the identical body with `Content-Type: text/plain`. Signal: 403 + support ID on the first, 200 with the app parsing the JSON on the second = profile gap. |
| Source | https://techdocs.f5.com/en-us/bigip-17-5-0/big-ip-asm-implementations/adding-json-support-to-an-existing-security-policy.html ; https://my.f5.com/manage/s/article/K000156619 |

## 8. ModSecurity + OWASP CRS

| Field | Detail |
|---|---|
| Position | Host module inside Apache/nginx/IIS (or embedded in a commercial WAF). No separate edge, so "origin" is the app itself and there is nothing to bypass by IP `[doc]` https://www.coreruleset.org/docs/ |
| Inspection / normalization | Anomaly scoring with paranoia levels: each matching rule adds score, the inbound threshold decides the block, and PL1 is the default deployment posture. `[doc]` https://www.coreruleset.org/docs/2-how-crs-works/ . Body handling is off unless request-body access is enabled and capped by `SecRequestBodyLimit` (13107200 bytes in the shipped recommended config) `[doc]` https://raw.githubusercontent.com/owasp-modsecurity/ModSecurity/v3/master/modsecurity.conf-recommended . Content-type determines which body processor runs `?`. |
| Block signature | Default disruptive action is `deny` → HTTP 403; CRS's stock error page is the Apache "Not Acceptable!" document `?`. Detector markers `server: mod_security`, body `ModSecurity` `[obs]`. |
| Weak spots | (a) Confirmed bypass classes at PL1 across multipart, JSON and XML: boundary continuation (`boundary=fake-boundary;boundary*0=real-;boundary*1=`), NUL in field names, content-type removal, charset case change — ModSecurity acknowledged all reported bypasses in CRS 3.3 `[res]` https://arxiv.org/abs/2503.10846 . (b) Higher PL means more rules, but PL1 is what most deployments run `[doc]` https://www.coreruleset.org/docs/2-how-crs-works/ . (c) Body over `SecRequestBodyLimit` is not buffered for inspection `[doc]` config URL above. |
| Test | `POST /` with `Content-Type: multipart/form-data; boundary=fake-boundary;boundary*0=real-;boundary*1=` and the payload between `--real-boundary` delimiters (WAFFLED's Figure example). Signal: 200 + app-side execution while the same payload inside `--fake-boundary` returns 403. |
| Source | https://arxiv.org/abs/2503.10846 ; https://www.coreruleset.org/docs/2-how-crs-works/ ; https://raw.githubusercontent.com/owasp-modsecurity/ModSecurity/v3/master/modsecurity.conf-recommended |

## Cross-vendor invariants

1. **A block verdict needs a soft-404 control.** Every engine above can return 403 for reasons unrelated to the payload (IP reputation, geo, missing session cookie). Send one random path and one benign path first; if both 403 with the same body hash, the block is ambient and no payload test is valid.
2. **Never infer "bypass" from status alone.** Confirmed non-403 outcomes per vendor: AWS Challenge = 202 `[doc]` https://docs.aws.amazon.com/waf/latest/developerguide/waf-captcha-and-challenge-actions.html ; AWS CAPTCHA = 405; Cloudflare challenge = 200/403 with `cf-mitigated: challenge` `[doc]` https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/ ; Akamai and Imperva deceptive 200s `[doc]`(secondary) https://www.statproxies.com/glossary/anti-bot-status-codes ; DataDome device check `[doc]` https://docs.datadome.co/docs/response-pages ; Kasada 429 `[doc]`(secondary) https://www.aethyn.io/blog/kasada-429-vs-rate-limit-misdiagnosis . The verdict unit is (status, response-body hash, protected-resource marker), not status.
3. **Raw sockets are mandatory.** `requests`/`urllib` normalize the request target and re-encode `%2e`, `%2f`, `//`, `..;/`, and collapse duplicate headers, destroying exactly the variants these engines disagree about (see the note in the detector's own header and the encoding classes in https://portswigger.net/web-security/essential-skills/obfuscating-attacks-using-encodings). Send the literal bytes, one variant per connection, HTTP/1.1 with explicit `Host`, and add an HTTP/2 variant because h2 header/`Content-Length` semantics differ and enable downgrade desync classes https://portswigger.net/research/http2 .
4. **Every inspection has a size window.** Cloudflare 128 KB Enterprise / 1 MB Free `[doc]` https://developers.cloudflare.com/waf/managed-rules/ ; AWS 8 KB ALB / 16 KB default / 64 KB max `[doc]` https://docs.aws.amazon.com/waf/latest/developerguide/waf-oversize-request-components.html ; Azure Front Door 128 KB `[doc]` https://raw.githubusercontent.com/MicrosoftDocs/azure-docs/main/includes/front-door-limits.md ; Cloud Armor 8–64 kB `[doc]` https://docs.cloud.google.com/armor/docs/configure-waf ; ModSecurity `SecRequestBodyLimit` `[doc]` https://raw.githubusercontent.com/owasp-modsecurity/ModSecurity/v3/master/modsecurity.conf-recommended . A payload placed past the window is a first-class test case, not an afterthought.
5. **Content-Type is a policy selector, not a fact.** F5 only parses JSON when a JSON profile is attached `[doc]` https://techdocs.f5.com/en-us/bigip-17-5-0/big-ip-asm-implementations/adding-json-support-to-an-existing-policy.html ; Cloud Armor's JSON parsing is off by default `[doc]` https://docs.cloud.google.com/armor/docs/content-parsing ; WAFFLED's highest-yield classes are content-type removal and body-parser switching, with 1207 confirmed bypasses and more than 90% of sampled real apps accepting a swapped content type `[res]` https://arxiv.org/abs/2503.10846 . Always send the same body under `application/json`, `application/x-www-form-urlencoded`, `multipart/form-data` and `text/plain`.
6. **Header trust is a per-engine decision, not a per-app one.** Cloudflare rewrites `accept-encoding`, drops `x-real-ip`, and can drop headers with invalid names `[doc]` https://developers.cloudflare.com/fundamentals/reference/http-headers/ ; AWS inspects only the first 8 KB / 200 headers and treats duplicate `Cookie` headers per its own merge `[doc]` https://docs.aws.amazon.com/waf/latest/developerguide/waf-oversize-request-components.html ; frameworks merge duplicate cookies differently, which is the entire phantom-cookie bypass `[res]` https://portswigger.net/research/bypassing-wafs-with-the-phantom-version-cookie . Test `X-Forwarded-For`, `X-Original-URL`, `X-Rewrite-URL`, duplicate `Cookie`, duplicate `Content-Length`, and `Transfer-Encoding: chunked` as separate probes; the differential signal is a change in blocked/allowed outcome while the app-visible resource is unchanged.
7. **Path normalization is the single richest mismatch.** Cloudflare documents that `/%68ello` and `/hello` are the same path and that `//` collapse cannot be disabled `[doc]` https://developers.cloudflare.com/rules/normalization/ ; WAF-vs-app path confusion and cross-library URL-parser disagreement are documented attack classes https://claroty.com/team82/research/exploiting-url-parsing-confusion . Sweep order that pays: `//`, `/%2e/`, `..;/`, `%2f`, `%5c`, `%00`, overlong UTF-8 `%c0%af`, `%u2215`, trailing `/.`, `?`/`#` truncation, and case variants of the path.
8. **Origin-IP discovery outranks every payload trick where it applies.** Sucuri documents the bypass and its own mitigation workaround `[doc]` https://docs.sucuri.net/website-firewall/configuration/prevent-sucuri-firewall-bypass/ ; Akamai's answer is Site Shield, a separate product `[doc]` https://techdocs.akamai.com/site-shield/docs/allow-site-shield-ip-addresses-through-your-firewall . Appliance/host engines (F5 BIG-IP, FortiWeb, Barracuda, ModSecurity, Wordfence, Imunify360) have no CDN hop to pivot through, so for those the equivalent move is a direct request to a non-proxied port, alternate vhost, or a subdomain that bypasses the WAF.
9. **Score-based engines need volume, signature-based engines need shape.** Akamai's per-group risk score `[doc]` https://techdocs.akamai.com/cloud-security/docs/set-protections and HUMAN's blocking score `[doc]` https://docs.humansecurity.com/applications/php/configuration mean one request proves nothing; the engine must replay the identical request N times and look for a threshold crossing, while keeping within the target's rate policy.
10. **Every positive needs a repeat.** Two identical raw-socket sends per variant, same bytes, fresh connection. A single 200 is cache, challenge, or luck; two matching non-block responses with the protected content present is the minimum bar before the row is reported as a bypass.
